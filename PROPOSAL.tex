\section*{Problem}

Summer 2027 internship postings go live across hundreds of company career pages starting August 2026. Today I find them by scrolling job boards and a community GitHub repo, manually, daily. Worse: as an international student (F-1), a large share of postings are citizenship-gated (ITAR, ``US persons only'', ``unable to sponsor''), and I usually discover that only after reading deep into the JD or after applying. Every international friend I have hits the same wall.

\section*{What it is}

A Go service that watches the career boards of a configurable list of companies and posts to a Discord channel when a new Summer 2027 SWE internship appears, with a flag for sponsorship risk. Discord is the entire user interface. There is no web frontend, by design.

\begin{center}
\begin{minipage}{0.85\textwidth}
\begin{verbatim}
Greenhouse / Lever / Ashby public JSON endpoints
                  |
      poller (worker pool, rate-limited, scheduled)
                  |
      normalizer (3 vendor schemas -> 1 Posting model)
                  |
      differ (vs Postgres: new? changed? closed?)
                  |
      filter (intern + 2027 + SWE, sponsorship-signal rules)
                  |
        +---------+---------+
        |                   |
  Discord webhook      REST API (query/search)
                            |
              Prometheus + Grafana (postings/hr,
              fetch latency, parser failures)
\end{verbatim}
\end{minipage}
\end{center}

\section*{Why not just use Simplify or existing job bots}

\begin{enumerate}
  \item Sponsorship-signal detection. No mainstream tool flags ``this posting smells citizenship-gated'' for F-1 students. That filter is the point.
  \item Closed-posting diffs. I want to know when a posting disappears, not only when it appears.
  \item Per-user filters when friends join (keywords, companies, sponsorship strictness).
  \item Honestly: the point is building it. This is my backend/infra learning project and I will be user \#1 daily from August.
\end{enumerate}

\section*{Data sources}

Public, documented JSON endpoints only. No scraping, no LinkedIn.

\begin{itemize}
  \item Greenhouse: \texttt{boards-api.greenhouse.io/v1/boards/\{company\}/jobs}
  \item Lever: \texttt{api.lever.co/v0/postings/\{company\}}
  \item Ashby: public posting API
  \item Company list seeded from community-maintained lists (a few hundred companies)
\end{itemize}

Known coverage gap: companies on Workday are out of scope for v1 (their API is much uglier).

\section*{Non-goals (v1)}

\begin{itemize}
  \item No web UI. Discord only. (Personal rule, 9 weeks minimum.)
  \item No ML for sponsorship detection. Rules and regex only.
  \item No Workday ingestion.
  \item No auth or multi-tenancy until friends actually ask to join.
  \item Not a startup. This is a resume project with one honest user at launch.
\end{itemize}

\section*{Risks and mitigations}

\begin{itemize}
  \item Unofficial endpoints can change or throttle. Mitigation: cache every raw API response to disk from day one, so development never blocks on upstream, and parser breakage is replayable.
  \item Depth is back-loaded and August is busy. Mitigation: worker pool moved forward to week 5, so a truncated project still has interview substance.
  \item Read-side load is tiny (a few friends). Mitigation: honest phrasing everywhere, ``load tested to X req/s'', never ``handles X req/s of traffic''.
  \item Crowded genre. Mitigation: the sponsorship filter and diffs are the differentiators, plus the answer in the section above.
\end{itemize}

\section*{Success criteria}

\begin{enumerate}
  \item From August, I personally find internships through this tool, not by scrolling.
  \item It survives 30 minutes of interview grilling: every component has a ``what broke and what I did'' story.
  \item Deployed, monitored, load tested, README, and I can explain every line.
\end{enumerate}
